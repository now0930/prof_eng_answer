## 왜 원복하는가

7개 legacy Topic의 48개 문장을 단문화해 `rubrics/topic_packs/*/fact_anchor.json`에 바로 반영했지만, `calibration/fact_anchor_simplification_review_20261114.json`은 이미 모두 `PENDING_TECHNICAL_REVIEW`였다. 문장 변경의 정확성, 출처 locator, 책임 Topic, routing/coverage/WRONG/Fatal 영향과 generated 재빌드·전체 pytest가 입증되지 않은 상태로 canonical source를 교체해서는 안 된다.

기능안전 Topic 원래 원본 `09e4b1c7`의 파일 SHA-256 **`cb1aa6021a942e9c76b2e6b809495613364a413a92fe8ecf942ff1e1b978c4fd`**는 promotion ledger의 해당 Topic 6행 `topic_source_sha256`과 정확히 동일하다. 단문 수정된 현재 source SHA-256은 `54cc62524ed406818164d4fc05f3524b3c66ce33c6e94080a37878783d25d4d7`. 그러므로 Registry/ledger 파일을 **무변경으로 보존한 원본 byte-level 복원**이 승인 계약 보존의 올바른 조치다.

## 변경 방식

- 기준 `09e4b1c7347c330b6196be695a4c0ac3a091531d`에 있던 아래 **7개 Git blob을 그대로 canonical fact_anchor.json 경로에 복원**한다. 48개 `previous_statement`가 각 원본 blob과, 48개 `simplified_statement`가 복원 직전의 원격 HEAD와 **48/48 일치함을 사전에 확인**했다. 다른 Topic Pack source를 건드리지 않는다.
- 후보 48개는 [기존 manifest](../calibration/fact_anchor_simplification_review_20261114.json)에서 삭제하지 않고 보존한다. `application_status=CANDIDATE_ONLY_NOT_APPLIED`, `applied_anchor_count=0`; 기존 `PENDING_TECHNICAL_REVIEW`/ `score_effect=none` 그대로. Manifest `changed_anchor_count=48`은 *단문화 제안 건수*이며 현재 적용 건수가 아니다.
- 감사기 `scripts/audit_fact_anchor_sentence_sync.py`는 pending manifest일 때 원본 문장과 source의 **정확 일치**를 요구한다. `source==candidate` 또는 다른 문장, 중복 ID 및 잘못된 manifest는 실패한다. generated 문장이 original/new/other/missing 중 어느 상태인지 **읽기 전용으로만** 표기한다.
- `tests/test_fact_anchor_simplification_batch.py`는 48개 후보의 한 문장·조건을 검증하는 동시에 **정본 source에 모두 이전 문장으로 남아 있어야 함**을 검사한다. `tests/test_fact_anchor_sentence_sync_audit.py`에 미승인 후보의 source 무단 적용, `applied_anchor_count` 허위 설정 거부 사례를 **추가**한다. 기존 Fact/Registry/ledger/hash/WRONG/Fatal/ceiling/generator assertions는 삭제하거나 완화하지 않는다.

## 판정 및 실행 경계

- **기능안전 승인 불일치 3건과 ledger source-hash 불일치 2건의 원인 상태를 원본으로 복원함.** 이는 파일 해시와 기존 guard 조건상 **수정 근거**이지 현재 HEAD `pytest PASS`가 아니다.
- Generated 6개 파일은 `09e4b1c7`과 원격 Git blob이 같고 builder도 동일하므로 7개 canonical source를 복원하면 *코드/입력 수준에서* freshness가 맞을 것으로 예상된다. **Generated를 직접 만지지 않았고 새 리빌드/테스트는 실행 전**이다. 어떤 head에서든 생성된 6파일 byte-diff / generated manifest / source-to-ledger checks는 실제 release에서 확인할 것.
- 변경 대상 외 Topic, Fact IDs, 기존 Registry, review ledger, source 리뷰 증거, A/B/C 결정론, D/E, grading exclusion, Fatal, score ceiling, Golden 및 routing 코드 모두 그대로. `review_status`를 APPROVED로 변경하지 않는다.
